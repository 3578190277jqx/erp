## 四个实现取舍

1. **可靠身份才配对。** 唯一有效 code 优先，之后才是唯一有效 id，且两侧集合必须相同。重排单列。代价：不明确的条目仍需查看整体明细，避免错误归因。
2. **完整 before 与精简 after 共同构成证据。** after 仅留变化状态、实际查询字段及必要规则。代价：操作后的未变上下文须从 before 读取；原始历史日志不做压缩回写。
3. **仅已知并发版本归技术层。** id/code/object_id 改变仍属可见业务事实。代价：真实身份或关联变化会增加业务计数，这是有意保留的提醒。
4. **列表/CSV 与审计使用不同时间密度。** 前者本地分钟无偏移，后者本地秒及偏移。代价：CSV 的时区来自系统约定、只有分钟精度；不保证所有表格软件自动识别。

## 既定业务口径

报告末尾累积问题已有决策，本轮沿用，不重新改规则：

- 停用合作阻止普通双方新增共享；管理员例外仍留审计，历史读取与有范围的源端治理保留。
- 停止原因仅源门店可见，不扩大工厂读取。
- 附件操作推进独立 epoch，不推进父单业务版本。
- 历史产品口径确认不强制修改合同额。
- 订单变更逐单审批；其他已支持模块的批量操作保留。
- 等长列表按 AA1 的可靠身份比较，不引入新的 TRANSITIONS/effects 重构。
